sdtools — architecture

console tool → run API + dispatcher → worker fleet → cheap summariser → dashboard / Plane

Five loosely coupled components. The seam between the CLI and the API is a versioned wire contract; the seam between the API and your dashboard is REST. Any one component can be replaced without touching the others. The telemetry plane is drawn first; the dispatch plane (submit from one computer, execute on many machines) follows below.

The dispatch plane — one computer submits, many machines execute

Pull-based: workers poll, so no inbound access to field machines is needed. Claims follow a stated total order — (priority, created_at, job_id) per queue — and every claim is a renewable lease, so a machine that dies loses the lease and the job retries elsewhere.

Why client-generated run ids

A run gets its UUID before it talks to the server, so a job that starts offline keeps one identity when its telemetry arrives later — and replay is idempotent.

Why the digest is the cache key

Summaries are keyed on (log_digest, prompt_version), not run id. An identical rerun costs nothing. It also means the prompt carries no identity — a name in it would leak across shared summaries.

Why reduce before the model

95% of a long log is one line with a different number. Collapsing by shape while keeping every error makes the summary both cheaper and better — token count stops depending on job length.

Why heartbeats

Without them, "running" and "the laptop closed two hours ago" look identical. The sweeper turns silence into status = lost.
